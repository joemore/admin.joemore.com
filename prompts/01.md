## 5. Secure authentication

Implement real Supabase email/password authentication using current SSR best practices.

Requirements:

- Use `@supabase/ssr`.
- Set up separate browser and server Supabase clients.
- Use Next.js 16 `proxy.ts` for appropriate session refresh.
- Use verified authentication claims or fresh server-confirmed user information, not untrusted session objects, for authorisation.
- Store sessions correctly using secure cookie-based SSR patterns.
- Protect all dashboard pages server-side.
- Protect any Server Actions and Route Handlers individually.
- Do not rely exclusively on frontend redirects or proxy checks for security.
- Verify the current user's active membership in `admin_users`.
- Sign Out must terminate the Supabase session and return to `/login`.
- Authenticated non-admin users must be denied access.
- Unauthenticated users must be redirected to login.
- Prevent caching or sharing of private authenticated page responses.
- Handle expired sessions and connectivity failures gracefully.
- Never include passwords, access tokens or secret keys in logs.

Cloudflare Access will eventually provide an additional outer security layer, but the application must remain independently secure without it.

## 6. Create the database schema structure

Add this directory:

`supabase/schemas/`

Store the SQL database definitions and RLS policies here.

For v0.0.1, create an ordered, clearly documented set of SQL files representing the admin security foundation.

For example:

- `001_admin_users.sql`
- `002_admin_access.sql`
- `README.md`

These filenames are suggestions. Choose a clean structure that will remain maintainable as the database grows.

Avoid creating duplicate, divergent SQL definitions in multiple directories. Document the source of truth and how future changes will be versioned or migrated.

### Create `public.admin_users`

Required columns:

| Column     | Type        | Requirements                      |
| ---------- | ----------- | --------------------------------- |
| user_id    | UUID        | Primary key, FK to auth.users(id) |
| role       | TEXT        | Required, constrained roles       |
| is_active  | BOOLEAN     | Required, default true            |
| created_at | TIMESTAMPTZ | Required, default now()           |
| created_by | UUID        | Optional FK to auth.users(id)     |

For roles, support:

- `super_admin`
- `admin`
- `editor`

Initially, only my account will have `super_admin`.

Set appropriate foreign-key deletion behaviours.

Use the auth user UUID as the authoritative identity, not an email address.

### Row Level Security

Enable RLS on `public.admin_users`.

Security rules:

1. Anonymous users have no access.
2. An ordinary authenticated user cannot read other users' admin records.
3. An authenticated user may read only their own admin record.
4. No browser-authenticated user can insert an admin record.
5. No browser-authenticated user can edit their admin role or active status.
6. No browser-authenticated user can delete admin records.
7. Admin membership must be granted or revoked through trusted database administration, not self-registration.
8. Explicitly review and set PostgreSQL table privileges, not just RLS policies.

In this first version, it is acceptable for even a `super_admin` to be unable to modify admin membership through the browser.

We will build administrative user management separately in a future release.

### Create a reusable admin-check helper

Create a PostgreSQL function along the lines of:

`private.is_admin()`

Requirements:

- No arbitrary user ID supplied by the caller.
- Determine the user from the authenticated request.
- Verify an active row exists in `public.admin_users`.
- Return true only for an active, permitted administrator.
- Return false for anonymous users, absent records and inactive administrators.
- Use a properly secured `SECURITY DEFINER` implementation only if justified.
- Pin the function's search path and schema-qualify references.
- Keep privileged helper functions outside publicly exposed API schemas.
- Explicitly restrict EXECUTE privileges.
- Avoid recursive RLS dependencies.

Design this helper for future content tables, where policies can check whether a signed-in user is an active administrator.

For the current dashboard, reading the current user's own RLS-protected `admin_users` row is also acceptable for determining their role.

**Critical:** The system must never allow a user to promote themselves by editing their account metadata or supplying a different UUID.
